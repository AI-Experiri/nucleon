# 0009 — 2026-08-15 — the MLX pivot

## What happened

User called the ADR-004 pure-Rust rule the wrong bet: MLX exists,
Apple maintains it, and the fused kernels our Metal chapter said we
would eventually build (tiled matmul, FlashAttention, simdgroup
intrinsics) are exactly what MLX ships at production quality. So
nucleon pivots to MLX for compute; hand-written Metal is off the
trunk.

Explicit user directives before I touched code:

- "Delete nucleon-metal entirely."
- "We will simply have a wrapper on mlx-rs so we can control it."
- "Restructure loader to have a formats folder."
- "The .metal shaders stay as book reference material for comparison."

## Commits, in order

1. `refactor(loader): move GGUF-specific files under formats/gguf/`
   — folder restructure only, tests still 115 green.
2. Tag `pre-mlx-pivot` on the loader-restructured commit so nothing
   below is truly lost.
3. `feat(mlx): pivot — nucleon-metal removed, nucleon-mlx scaffold`
   (this commit).

## Deleted

- `nucleon-metal/` entirely: `src/{lib.rs,device.rs,ops.rs,backend.rs,backend_tests.rs}`,
  `kernels/ops.metal`, `examples/fusion.rs`, `Cargo.toml`. About
  2500 lines including tests. Preserved in the tag.
- `nucleon/src/backend/`: the `Backend` trait, `CpuBackend`, its
  tests. About 800 lines including tests. Preserved in the tag.
- Workspace `Cargo.toml` deps that only backend needed:
  `anyhow`, `thiserror`, `bytemuck`, `memmap2`, `safetensors`,
  `serde`, `serde_json`, `tokenizers` (tokenizers returns with its
  chapter).

## Preserved

- `nucleon-metal/kernels/ops.metal` → `docs/book/src/reference/kernels/ops.metal`.
  Twelve kernel functions the Metal chapter and future benchmarks
  refer to.

## Added

- `nucleon-mlx/` crate. `mlx-rs = "=0.25.3"` exact-pinned as an
  OPTIONAL dep behind a `mlx` feature (default off) because
  `cargo check --workspace` blew up on first build: `mlx-sys`'s
  bindgen tripped a size-assertion (`arm64-apple-darwin` vs
  `aarch64-apple-darwin`, `left: 4 right: 8`), traced to the ESP32
  xtensa-esp-elf toolchain on my PATH confusing clang's target
  detection when `mlx-sys/build.rs` invokes cmake. Follow-up: fix
  the build env in isolation (probably a `.cargo/config.toml` that
  scrubs the ESP paths, or explicit CC/CXX pinning) BEFORE the
  family forward pass block starts, since that's when we first need
  real MLX ops.
- Public API today (no feature): `mlx_rs_version()`,
  `mlx_c_version()`, `mlx_version()`, `version_triple()` — the four
  functions the book chapter promised. With `mlx` feature on:
  re-exports of `Array`, `Device`, `Dtype`, and `ops`.
- `docs/decisions/005-compute-via-mlx-rs.md` supersedes ADR 004.
  Names the version-cadence discipline, the pin/absorb rhythm, and
  the ladder (contribute → fork → write our own bindings over mlx-c)
  if oxideai's `mlx-rs` falls too far behind Apple.

## What stayed the same

- Loader is untouched functionally. `Yamf.tensors` remains
  `HashMap<String, nucleon::tensor::Tensor>`; migration to
  `nucleon_mlx::Array` happens with the family block so this pivot
  does not have to rewrite the 115 loader tests.
- `nucleon::tensor::Tensor` still exists (loader border needs it).
  When Yamf's tensor type flips, whether the standalone Tensor stays
  or dissolves is decided then.
- Book: chapter 3 (MLX) already documents this pivot with the pinned
  triple, composed-vs-fused, and the fused-ops table for Qwen3.
  Metal chapter (was "Metal 0") already renamed and its section 4.9
  (Backend trait attach) and 4.10 (upcoming Metal topics) already
  removed in the previous commit, with a new 4.9 handing the reader
  to the MLX chapter.
